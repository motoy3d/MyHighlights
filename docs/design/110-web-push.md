# #110 Web プッシュ通知 設計

2026-09-21 作成。対象は Laravel 13 / PHP 8.4 / Vue 2 + Onsen UI の新サーバ
（`feature/upgrade-laravel13-php84-al2023`）。

## 1. 目的

LINE Notify の終了（2025 年 3 月）で、通知手段はメールだけになった。
利用者の約 6 割はホーム画面のアイコンから起動しており、iPhone でも Web プッシュが届く
（iOS 16.4 以降。Google Analytics で見る限り、実際に使っている iPhone はすべて該当する）。

プッシュ通知を足して、次を実現する。

- 新しい投稿・予定の変更や中止を、アプリを開かなくても知らせる
- 通知をタップしたら、その投稿や予定が開く
- メールよりも通知を細かく選べるようにし、「うるさいので全部切る」を防ぐ

## 3. 今の通知の仕組み（調査結果）

| きっかけ | 宛先 | 条件 |
| --- | --- | --- |
| 新しい投稿 | チームの全員（メール通知オンの人） | **常に送る**。投稿画面の「みんなにメール通知」スイッチはコメントアウトされており、`posts.notification_flg` は使われていない |
| 投稿へのコメント | チームの全員 | コメントした人がベルをオンにしていれば（既定はオン） |
| 予定へのコメント | チームの全員 | 同上 |
| 予定の登録・変更 | — | **送っていない**。スイッチがコメントアウトされたまま |

- 送信は `PostNotificationJob` / `ScheduleNotificationJob`（キュー経由）。SES の送信レートを守るため、1 通ごとに 1〜2 秒待っている
- **予定へのコメントの大半（約 86%）は出欠連絡なので、「参加します」の一言ごとにチーム全員へメールが飛んでいる。**
  メール通知をオフにした人が約 3 人に 1 人いるのは、これが一因と見られる。
  プッシュで同じ送り方をすると、すぐに通知を切られる

## 4. 通知の種類と宛先

| 種類 | 宛先 | 既定 | 段階 |
| --- | --- | --- | --- |
| 新しい投稿 | チームの全員 | オン | 1 |
| 自分の投稿・自分がコメントした投稿へのコメント | 投稿者と、その投稿にコメントした人 | オン | 1 |
| その他の投稿へのコメント | チームの全員 | **オフ** | 1 |
| 予定の変更・中止 | チームの全員 | オン | 1 |
| 予定へのコメント | 予定を作った人と指導者 | オン（指導者のみ） | 1 |
| 出欠の未回答への催促 | 未回答の保護者 | オン | 2（#109 と一緒に） |
| 予定のリマインド（前日など） | チームの全員 | 選択制 | 2（#29） |

- 自分の操作による通知は、自分には送らない
- 「予定の変更・中止」は新しい通知
  - 予定の編集画面に「変更をみんなに通知する」スイッチ（既定オン）を置き、オンのときだけ送る
  - さらに、**日付・開始時刻・終了時刻・終日・タイトルのいずれかが変わったときだけ**送る。
    メモ欄だけの修正では送らない（予定の表に「場所」「中止」の列は無く、中止はタイトルの書き換えか削除で表される）
  - **今日以降の予定を削除したとき**は「中止」として送る（過去の予定の整理では送らない）
- メール通知の宛先は今回は変えない（別の判断が要るため）。プッシュの宛先だけを上の表にする

## 5. 全体の構成

```
[画面(Vue)] --購読--> POST /api/push/subscriptions --> push_subscriptions テーブル
[投稿・コメント・予定の保存] --> PushNotificationJob(キュー) --> Web Push サービス
                                                              (Apple / Google / Mozilla)
                                                                     |
[Service Worker(sw.js)] <----------- 暗号化された通知 --------------+
   └ 通知を表示 → タップ → /home?team=…&post=… を開く
```

## 6. クライアント側

### 6.1 Service Worker

- `public/sw.js` に置く（Vite のビルド対象にしない。URL を固定し、スコープを `/` にするため）
- 扱うのは `push`（通知を表示）と `notificationclick`（該当画面を開く。アプリが開いていればそのウィンドウを使う）だけ。
  **`fetch` は扱わない（キャッシュしない）**。キャッシュを入れると古い画面が残る問題が起きやすいので、今回はやらない
- 同じ投稿へのコメントが続いたときに通知が積み上がらないよう、`tag`（例 `post-123`）で置き換える

### 6.2 購読と設定画面

設定画面の「メールで通知を受け取る」の下に「この端末で通知を受け取る」を追加する。

- オンにしたとき（＝利用者の操作をきっかけに）通知の許可を求める。iOS は操作をきっかけにしないと許可を求められない
- 許可されたら `PushManager.subscribe()` し、購読情報をサーバへ送る
- 端末ごとの購読なので、同じ人が iPhone と PC の両方でオンにできる
- 通知の種類ごとのオン・オフ（§4 の表）はユーザー単位で持つ
- 通知が使えない状態のときは、スイッチの代わりに理由を出す
  - iPhone でホーム画面から起動していない → §6.3 の案内
  - 通知を拒否している → 端末の設定から許可する手順
  - 古い端末 → 「この端末では使えません。メール通知をご利用ください」

### 6.3 ホーム画面への追加の案内（#55）

- iPhone の Safari で開いていて、ホーム画面から起動していないとき、設定画面とタイムラインの上部に案内を出す
  （「共有ボタン → ホーム画面に追加」の図入り。閉じたら一定期間出さない）
- Android の Chrome では `beforeinstallprompt` を受けて「ホーム画面に追加」ボタンを出す

### 6.4 通知から該当画面を開く（#9 の最小版）

- 通知のリンクは §7.3.1 の形（予定のリンクには、カレンダーでその日を開くための `date` を付ける）
- 起動時にパラメータを読み、次の順で処理する
  1. `team` が今のチームと違えば、チームの Cookie を切り替える（所属していないチームはサーバのミドルウェアが正す）
  2. `post` なら投稿の詳細を開く（タイムラインで投稿を開く処理と同じ）。`schedule` ならカレンダーを開いてその予定を表示する
  3. 処理が終わったら `history.replaceState` でパラメータを消す（再読み込みで同じ画面が開き直さないように）
- 同じリンクを通知メールの本文にも入れる（#9 の本来の要望）

## 7. サーバ側

### 7.1 ライブラリ

`laravel-notification-channels/webpush` 13.x（2026-09 時点で Laravel 13 に対応。内部で `minishlink/web-push` 11 を使う）。
PHP 拡張は curl / openssl / mbstring が必須。gmp は任意（あると暗号化が速い）。新サーバで有無を確認する。

### 7.2 データ

- `push_subscriptions`（ライブラリのマイグレーション）：ユーザーごと・端末ごとの購読情報
- `users` に通知の種類ごとのオン・オフを追加する（`push_prefs` の JSON 1 列。種類が増えてもマイグレーションが要らない）

### 7.3 API（画面とサーバの取り決め）

既存の API と同じ認証（Sanctum）とチームのミドルウェア（`auth:api`, `team`, `log`）の下に置く。

| メソッド | パス | 送るもの | 返すもの |
| --- | --- | --- | --- |
| GET | `/api/push/config` | — | `{ enabled, vapid_public_key, preferences }` |
| PUT | `/api/push/preferences` | `{ preferences: {...} }` | `{ preferences }` |
| POST | `/api/push/subscriptions` | `PushSubscription.toJSON()` の形 `{ endpoint, keys: { p256dh, auth } }` と `content_encoding` | 204 |
| DELETE | `/api/push/subscriptions` | `{ endpoint }` | 204 |
| POST | `/api/push/test` | — | この利用者の全端末にテスト通知を送る。送った件数 `{ sent }` |

- `enabled`：§8 の段階的な公開の判定結果。`false` のとき画面はスイッチを出さない
- `preferences` のキーと既定値

  | キー | 意味 | 既定 |
  | --- | --- | --- |
  | `new_post` | 新しい投稿 | true |
  | `comment_on_mine` | 自分の投稿・自分がコメントした投稿へのコメント | true |
  | `comment_on_others` | その他の投稿へのコメント | false |
  | `schedule_change` | 予定の変更・中止 | true |
  | `schedule_comment` | 予定へのコメント（届くのは予定を作った人と指導者だけ） | true |

- 予定の更新 API（`PUT /api/schedules/{id}`）に `notify_change`（`'true'` / `'false'`）を追加する

### 7.3.1 通知の中身（Service Worker に届く JSON）

```json
{ "title": "チーム名", "body": "山田さんが投稿しました：9/27 練習試合のお知らせ",
  "tag": "post-123", "data": { "url": "/home?launcher=true&team=41&post=123" } }
```

- リンクの形
  - 投稿：`/home?launcher=true&team={team_id}&post={post_id}`
  - 予定：`/home?launcher=true&team={team_id}&schedule={schedule_id}&date={YYYY-MM-DD}`（予定を ID で取る API が無いので、カレンダーでその日を開くために日付を付ける）
- `tag` は `post-{id}` / `schedule-{id}`。同じ投稿へのコメントが続いても通知が積み上がらない
- 本文は 60 文字程度で切る

### 7.4 送信

- `PushNotificationJob` を新設し、既存のメール送信ジョブとは**別のジョブ**にする
  （メールは 1 通ごとに待つので、同じジョブにするとプッシュが遅れる）
- 宛先の決め方は §4。退会者・通知オフの人・操作した本人は除く
- 送信は `minishlink/web-push` のまとめ送り（`flush`）で行い、待ちは入れない
- Web Push サービスが 404 / 410（購読が無効）を返したら、その購読を削除する
- 通知の中身（タイトル・本文・リンク）は Web Push の仕組みで端末まで暗号化される。
  ロック画面に表示されるので、本文は冒頭の 60 文字程度に切る

### 7.5 鍵（VAPID）

- `php artisan webpush:vapid` で作り、`.env` に置く（リポジトリには入れない）
- **鍵を作り直すと、全員の購読が無効になる。** 新サーバで作った鍵を切り替え後もそのまま使う。
  切り替え当夜の `.env` の書き換え手順で消さないよう、チェックリストに追記する

## 8. 段階的な公開

- 設定に `PUSH_ENABLED_EMAILS`（カンマ区切りのメールアドレス）を用意し、ここに入っている利用者にだけ設定画面のスイッチを出す。`*` なら全員に出す。空なら誰にも出さない
  （ユーザー ID ではなくメールアドレスにしたのは、検証用アカウントを作り直すたびに ID が変わるため）
- **購読した端末にしか通知は届かない**ので、スイッチを見せない限り一般の利用者には何も起きない
- 順番
  1. 新サーバ（切り替え前）で、検証用アカウントとデスクトップの Chrome で確認する
  2. 切り替え後、本番で自分のアカウントだけに開放し、iPhone で確認する
  3. 指導者数名に開放して 1〜2 週間様子を見る
  4. 全員に開放し、お知らせの投稿を出す

## 9. 検証

| 対象 | 方法 |
| --- | --- |
| 宛先の決め方・購読 API・無効な購読の削除 | PHPUnit（通知の送信は偽物に差し替えて、誰に何が送られたかを確かめる） |
| 設定画面のスイッチ・ホーム画面追加の案内・起動時のリンク処理 | Playwright（通知の許可はテスト側で与える） |
| 実際に通知が届くか | 新サーバにポートフォワードでつなぎ、インストール済みの Google Chrome（画面ありで起動）で購読 → 別アカウントで投稿 → 通知が表示され、タップで該当の投稿が開くことを確認する。Playwright に同梱の Chromium は Google のプッシュサービスに接続できないため使わない |
| iPhone | 切り替え前は新サーバに iPhone から接続できないため、切り替え後に §8 の手順 2 で確認する |

新サーバは今 `MAIL_MAILER=log` で、メールは実際には送られない。プッシュは購読した端末にしか届かないので、
検証中に一般の利用者へ通知が飛ぶことはない。

## 11.1 検討時の論点（記録）

1. **予定へのコメント（出欠連絡）のプッシュの宛先**：案は「予定を作った人と指導者だけ」。今のメールと同じく全員に送るか
2. **予定の変更・中止の通知を新しく作るか**：案は作る（日付・時刻・場所・中止が変わったときだけ）
3. **夜間の扱い**：案は第 1 段階では区別しない（すべて即時）。「22〜6 時はコメントの通知を朝まで待たせる」は第 2 段階で検討
4. **iPhone での確認の時期**：案は切り替え後に自分のアカウントだけで行う。切り替え前に確認したい場合は、確認用のホスト名（DNS・証明書・セキュリティグループの開放）を別に用意する必要がある
