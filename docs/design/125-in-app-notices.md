# #125 アプリ内のお知らせ一覧（🔔） 設計

関連：#110（Web プッシュ通知。`docs/design/110-web-push.md`）、#123（アイコンのバッジ。`docs/design/123-app-badge.md`）

## 1. 目的

届いた通知を、アプリの中で後から確認し、目的の画面へ移れるようにする。

#123 ではホーム画面のアイコンに「まだ見ていないお知らせ」の数を出したが、アプリを開くと 0 になるため、
何が届いていたのかが分からなかった（スマホの通知センターから消えていると確かめようがない）。

## 2. 画面

### 2.1 🔔（お知らせのボタン）

- タイムライン・カレンダー・メンバー・設定の各タブの上部（ツールバーの右）に置く
- **まだ開いていない通知の数**を、🔔の右上に赤い丸で出す（0 なら出さない。100 以上は「99+」）
- タップすると、お知らせの一覧を開く

### 2.2 お知らせの一覧

使われていない試作の画面（`Notifications.vue`。中身は固定の見本）を置き換える。

- 最近 30 日の通知を、新しい順に最大 100 件
- 1 件ごとに：本文（通知と同じ文）、届いた時刻（「3時間前」など）。チーム名は、複数のチームに所属している人にだけ出す
  （種類のアイコンは幅がそろわず文の始まりがずれるので出さない）
- **まだ開いていない通知**は背景の色を変え、左に青い丸を付ける（開いた通知も丸の場所は空けて、文の始まりをそろえる）
- タップすると、その通知は「開いた」になり、その画面に移る（通知をタップしたときと同じ処理）
  - 今のチームの投稿は一覧の上に横から重ねて開く。戻ると一覧に戻る（左端からのスワイプでも戻れる）
  - 予定は一覧を閉じて、カレンダーのタブで開く
  - 別のチームの通知は、そのチームに切り替えて（読み込み直して）開く
- 🔔の数が変わったら（投稿を開いてその投稿の通知がまとめて「開いた」になった、新しい通知が届いた等）、一覧を表示したまま読み込み直す
- 右上に「すべて確認済みにする」（投稿の「既読」と混同しないよう、「既読」という言葉は使わない。2026-09-28）
- 通知が無いときは「お知らせはありません」

## 3. 数の意味（2026-09-24 決定）

| | 意味 | 減る・0 に戻るとき |
| --- | --- | --- |
| 🔔の数 | **まだ開いていない通知の数**（一覧の青い丸の数） | 1 件開くたびに 1 減る。「すべて確認済みにする」で 0 |
| ホーム画面のアイコンの数 | 🔔の数と同じ | 同上。アプリや一覧を開いただけでは減らない |
| タイムラインのタブの数 | まだ読んでいない投稿の数（今のまま） | 投稿を読んだとき |

例：通知が 5 件届く → アイコン「5」 → アプリを開く → アイコンも🔔も「5」のまま → 🔔を開く → 「5」のまま
→ 1 件タップ → その画面へ移り、🔔もアイコンも「4」。

> はじめは「一覧を最後に開いた後に届いた通知の数」（一覧を開くと 0）にしたが、実機で試したところ
> 一覧を開いただけで数が消え、まだ見ていない通知が残っているのに分からなかったため、この形に変えた（2026-09-24）。

### 3.1 「開いた」になるとき

- 一覧でタップしたとき
- スマホの通知をタップして、その画面に移ったとき（#110 のどの経路でも）
- **その投稿の詳細を開いたとき**（タイムラインから開いた場合も）。その投稿についての通知（新しい投稿・コメント）を
  まとめて「開いた」にする。予定はカレンダーで見ただけでは「開いた」にしない（どの予定を見たかを決めにくいため）

「開いた」になった通知は、**スマホの通知センターに残っていれば消す**（`registration.getNotifications()` から
その通知を探して `close()`）。

### 3.2 前面に戻ったときの帯（2026-09-25 決定、09-26 見直し）

iPhone でアプリがバックグラウンドのときに通知をタップすると、iOS の不具合でどの通知かがアプリに伝わらない。
画面からは通知センターの中身も見えない（`registration.getNotifications()` が空。2026-09-26 実機で確認）ので、
タップしたのか、触らずに戻ったのか、削除したのかは見分けられない。

そこで前面に戻ったときは画面を切り替えず、**バックグラウンドの間に届いて、まだ開いていない通知**を、
ツールバーの真下の帯で知らせる（`deep-link.js` の `checkArrivedWhileAway`、`NoticeBanner.vue` / `notice-banner.js`）。

- 1 件：🔔、チーム名（複数チームの人だけ）と届いた時刻、本文（2 行まで）、「開く」、✕。帯のタップでその画面を開き、「開いた」になる
- 2 件以上：「お知らせが N 件届いています」。帯のタップで🔔の一覧を開く（どれを開くかは一覧で選ぶ）
- ✕か 8 秒で消える。帯を出したまま別の画面に移った（画面を開く・戻る・タブを切り替える）ときも消す。通知は「まだ開いていない」のまま🔔に残る
- 開くときは今の画面の上に重ねる（投稿は横から開き、戻ると元の画面。見ている投稿と同じ投稿なら重ねずに開き直す）。
  予定は、見るだけの画面（投稿・お知らせ一覧）を閉じてカレンダーのタブで開く（入力中の画面は閉じない）
- お知らせの一覧を見ているときは帯を出さない（一覧が新しい通知を出す）
- 返す通知は最大 20 件（`NoticeLog::RECENT_MAX`）なので、それ以上届いていても「20件」と出る
- ホーム画面のアプリで、通知を許可し、この端末が購読しているときだけ（それ以外の端末には通知が届いていない）
- アプリが終了していたとき・Android は、通知のタップで自動で開く

> はじめ（09-25）は「通知センターから 1 件だけ消えていたら、それがタップされた通知」として帯を出していたが、
> 画面から通知センターが見えていなかったため、実際は「届いたのが 1 件なら出す・2 件以上なら出さない」になっていた。
> 見えないものを推測するのをやめ、届いた通知をそのまま知らせる形にした（2026-09-26）。

### 3.3 アプリを表示している間に届いた通知（iPhone。2026-09-26 決定）

iPhone では、アプリを表示している間に届いた通知を、sw.js から画面に知らせられない。
実機の診断で、通知を受けた sw.js から開いている画面が見えず（`clients.matchAll` が 0 件）、
`postMessage` も `BroadcastChannel` も画面に届かないことを確かめた。そのため🔔の数が増えなかった。

- **表示している間は、🔔の数を 30 秒ごとにサーバに聞き直す**（`push.js` の `installNoticeCount`。iPhone だけ。バックグラウンドの間は聞かない）
- 上部に出た通知のタップは、多くの場合アプリを読み込み直してその画面を開く（アプリが終了していたときと同じ）。
  ただし**何も起きないことがある**（2026-09-26 実機で 9 回中 3 回。起動の仕方や待った時間との関係は見つからず、
  iOS の不具合が表示している間にも不定期に起きているとみられる）
- **受け入れている弱点（2026-09-26 決定）**：表示している間に届いた通知は、タップで開かないことがある。
  🔔の数は 30 秒以内に増えるので、一覧から開ける。表示している最中に通知が来る場面は比較的少ないので、
  アプリの中に帯を重ねて出すことはしない

## 4. 誰に載せるか（2026-09-24 決定）

- **スマホの通知を使っていない人にも載せる**（PC だけの人、通知を許可していない人）
- 載せる相手は、プッシュ通知の宛先と同じ決め方（`PushRecipients`）：
  段階的な公開の対象、通知の種類ごとの設定がオン、そのチームに在籍中、操作した本人は除く
- プッシュ通知は、そのうち購読している端末がある人にだけ送る（今のまま）
- 段階的な公開（`PUSH_ENABLED_EMAILS`）の間は、🔔も対象の人にだけ出す（`/api/push/config` の `enabled`）

## 5. サーバ側

### 5.1 データ

#123 で作った `push_notices` を、アプリ内のお知らせにも使えるよう広げる。名前も `notices` に変える
（スマホに送らなかった通知も入るため）。

| 列 | 内容 |
| --- | --- |
| id | |
| user_id | 相手 |
| team_id | どのチームの通知か（**追加**。一覧のチーム名と、開くときのチームの切り替えに使う） |
| type | `new_post` / `post_comment` / `schedule_change` / `schedule_deleted` / `schedule_comment` / `test`（**追加**。一覧のアイコン） |
| nid | 通知ごとの目印（#110） |
| tag | `post-123` など。「その投稿を開いたとき」にまとめて開いたにするのに使う |
| title | 通知の題名＝チーム名（**追加**） |
| body | 通知の本文（**追加**） |
| url | 開く画面 |
| opened_at | 開いた時刻（**追加**。NULL ならまだ開いていない） |
| created_at | 届いた時刻（ミリ秒まで） |

- #123 で足した `users.push_seen_at` は使わなくなったので消す（数は `opened_at` が NULL の件数で出す）
- 30 日より前の行は、記録するときにその人の分を消す（今のまま）

### 5.2 記録

`PushNotificationJob` は、宛先の**全員**に記録する（購読の有無を問わない）。そのうえで、購読のある人にプッシュ通知を送る。
記録してから送るので、通知の `data.badge`（アイコンの数）はその人の「まだ確認していない数」をそのまま使える。

### 5.3 API

| メソッド | パス | 送るもの | 返すもの |
| --- | --- | --- | --- |
| GET | `/api/notices` | — | `{ unopened, items: [{ id, nid, type, team_id, title, body, url, opened, created_at }] }`（最近 30 日、新しい順に最大 100 件） |
| GET | `/api/notices/unopened` | — | `{ unopened }`（🔔の数。軽い問い合わせ） |
| POST | `/api/notices/open` | `{ nid }` または `{ all: true }` | その通知（またはすべて）を開いたにする → `{ unopened }` |

- 投稿の詳細（`GET /api/posts/{id}`）を返すときに、その人の `tag = post-{id}` の通知を開いたにし、
  開いた後の🔔の数を `unopened` として返す（段階的な公開の対象外の人には `null`）
- #123 の `POST /api/push/seen` は廃止する（アプリを開いただけでは消さなくなるため）
- #110 の `POST /api/push/recent` は `notices` から、まだ開いていない通知だけを返す（帯に出すので `team_id`・`title`・`body` も返す。§3.2）

## 6. クライアント側

### 6.1 🔔の数とアイコンの数を合わせる

- 🔔の数は `push.js` の `noticeState.unopened` に持つ
- 次のときに `GET /api/notices/unopened` で取り直し、アイコンの数も同じにする（`setAppBadge(n)`、0 なら `clearAppBadge()`）
  - アプリの起動時・前面に戻ったとき
  - アプリを開いている間に通知が届いたとき（sw.js が画面に「届いた」と知らせる。`postMessage`。iPhone では届かない。§3.3）
  - iPhone で表示している間は 30 秒ごと（§3.3）
- 通知を開いたとき（`POST /api/notices/open`）は、応答の数に合わせる（一覧でタップしたときは先に 1 減らしておく）
- 投稿の詳細を開いたときは、応答の `unopened` に合わせる
- 問い合わせている間に数が変わったら（通知を開いた等）、その問い合わせの応答は古いので使わない

### 6.2 Service Worker（`public/sw.js`）

- 通知を表示するときに、`data.badge` でアイコンの数を更新する（今のまま）
- 開いている画面に `{ type: 'notice-arrived' }` を知らせる（🔔の数を取り直させる。iPhone では画面に届かない。§3.3）

### 6.3 通知をタップして開いたとき

`deep-link.js` の各経路（sw.js からの知らせ・書き置き・帯・起動時のリンク）で開いたときに、
`POST /api/notices/open { nid }` を送る。起動時のリンクには `nid` が無いので、リンクに `&nid=` を足す
（`PushNotice` の `url` と `navigate`）。

## 7. テスト

- PHPUnit
  - 宛先の全員に記録され、購読のある人にだけプッシュ通知が送られる
  - 種類ごとの設定でオフの人、操作した本人、退会した人には記録しない
  - `GET /api/notices`：本人の分だけ、新しい順、30 日以内、`opened` の値
  - 🔔の数はまだ開いていない通知の数で、一覧を開いただけでは減らず、開いた分だけ減る
  - `open`：nid で 1 件／すべて。他人の通知は開いたにできない
  - 投稿の詳細を開くと、その投稿についての通知が開いたになり、開いた後の数（全チームの合計）を `unopened` で返す。公開の対象外の人には返さない
  - `push/recent` は開いた通知を返さない
  - `data.badge` が🔔の数と同じ
- Playwright
  - 🔔に数が出る／一覧に並ぶ／一覧を開いても数は減らない／タップで投稿が一覧の上に開き、数が 1 減り、戻ると一覧に戻る
  - 一覧から投稿を開いて戻ると、同じ投稿の他の通知も「開いた」で出る（読み込み直す）／スワイプで戻る
  - 通知が 0 件のときの表示／すべて確認済みにする／削除された投稿
  - 段階的な公開の対象外の人には🔔が出ない
  - タイムラインから投稿を開くと🔔がすぐ減る／通知から開いた投稿がタイムラインでも既読になる
  - iPhone で表示している間は 30 秒ごとに数を聞き直し、バックグラウンドの間は聞かない
  - 前面に戻ったときの帯：1 件で開く／2 件以上で一覧／✕／購読していない端末と Android では出さない／
    帯から開いた投稿の上に重ねても、戻った投稿での操作はその投稿に行く／同じ投稿は重ねない／
    予定は投稿を閉じてカレンダーで開く／一覧を見ているときは出さない／別の画面に移ると消える
- 実機（iPhone）：§7.1

### 7.1 実機（iPhone）での確認の例

2026-09-26〜27 に、確認用サーバとホーム画面に追加したアプリで行った（#110・#123・#125 と移行の確認をまとめたもの）。
本番に切り替える前や、通知まわりを変えたときに、この表を使って確かめる。

**準備**
- 通知を起こす側（別のアカウントでの投稿・コメント・予定の変更・削除）は、確認する人とは別の人が行う
- 変更を反映した後は、アプリを完全に終了（アプリの切り替え画面で上にスワイプ）してから開き直す。古い版が残るため
- 「アプリを終了している」ときは完全に終了、「裏に置いている」ときはホーム画面に戻るだけ（終了しない）
- 裏に置いているときのケース（C）は、アプリを裏に置いてから通知を送る。1 ケースごとに通知を送り直す
